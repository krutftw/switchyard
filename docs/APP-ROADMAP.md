# Switchya: product direction and first milestone

Research snapshot: 3 October 2026. Sources below are current official product documentation or the projects' own repositories. This is a documentation comparison, not a hands-on ranking. Main-branch documentation can describe work ahead of a released build; release versions must be pinned before comparative tests.

## Recommendation

Build a coding-first Switchya app and CLI around the existing gateway. Keep the gateway independently installable and useful to other tools. The first product promise should be: **take a repository task from request to a reviewable, tested change, and recover the work clearly when a model, process, or connection fails.**

The proposed audience is developers and small teams who already use several models or coding agents and own real repositories. That audience and its willingness to switch or pay remain hypotheses. A broad “super AI app” can be the longer-term direction, but chat, dictation, image generation, and a plugin marketplace do not establish a competitive advantage for the first coding release.

The product has three related surfaces:

- **Switchyard Gateway:** the existing self-hosted API endpoint, protocol translation, routing, credential pools, and operational dashboard.
- **Switchya App:** project and task workspace, live work, approvals, terminal, diff review, recovery, and completion evidence.
- **Switchya CLI:** the same task runtime and stored task state for terminal and scripted use. App/CLI handoff should not create unrelated conversations or replay completed changes.

These are the product boundaries. The app and task runtime are under development on the feature/agent-workspace branch; the acceptance benchmarks below remain unproven until their recorded checks pass. The public gateway currently documents four client protocols, streaming, WebSockets, routing/failover, and usage/cost visibility. It uses provider API keys or service accounts; consumer-subscription login is not an existing gateway capability. [Switchyard Gateway README](https://github.com/krutftw/switchyard)

## Focused advantage to test

**Hypothesis: Switchya can make multi-provider coding work easier to recover, audit, and finish within a known budget.** The existing gateway gives a useful starting point for this combination, but does not prove the advantage.

1. **One task record across providers and surfaces.** Store the requested outcome, constraints, decisions, workspace state, tool results, approvals, and verification obligations. A model change or app/CLI handoff continues the task; the user should not have to reconstruct a conversation. Preserve original events alongside summaries.
2. **Recovery with explicit uncertainty.** Distinguish queued, running, interrupted, awaiting approval, failed, and verified states. If the process dies after a command may have taken effect but before its result is stored, reconcile the result or ask for a specific decision. Do not blindly repeat it or claim general exactly-once command execution.
3. **Completion evidence attached to the change.** Show the actual diff, tests and exit results, provider/model route, remaining failures, and what was not checked. Invalidate verification when the relevant code or environment changes. “Agent finished speaking” and “requested work passed verification” must be separate states.
4. **Visible routing and spend.** Explain model choice and failover, show known token usage and pricing assumptions, and stop admitting work at a configured limit. Separate billed usage, provider-reported usage, estimates, and unknowns. External coding engines may not route through the gateway or expose complete usage, so do not promise comprehensive metering for every adapter.

The proposed advantage is the measured end-to-end workflow. Its ingredients overlap with competitors, including T3's durable orchestration and Pi's durable runtime. No current evidence establishes “best harness,” lower cost, greater reliability, unique recovery, or willingness to pay for Switchya.

## First working milestone: five acceptance benchmarks

The numbers below are proposed engineering targets, not observed results or market evidence. Keep the fixture repository, task wording, test oracle, model configuration, software versions, and machine details with each run.

| Benchmark | Proposed pass condition | Evidence retained |
| --- | --- | --- |
| **1. Real coding loop through app and CLI** | Six small repository tasks spanning a bug fix, a behavior addition, and a refactor. Each task runs from the same clean starting revision through both surfaces. At least five of six pass independent task tests on each surface using a configured real provider. All successful runs yield a reviewable diff; existing uncommitted user changes remain intact. A fixture-only demo cannot satisfy this live-model gate. | Starting revision, prompts, model/provider and settings, run logs, final diff, independent test output, wall time, usage, and human interventions. |
| **2. Interruption and handoff correctness** | Twenty deterministic interruption cases across pre-tool intent, active tool, result persistence, and UI reconnect boundaries. Zero lost accepted inputs, unauthorized repeat side effects, or false success states. App/CLI reconnection displays the recovered state within 10 seconds on the reference machine. Uncertain non-idempotent work is explicitly marked for reconciliation. | Failure injection point, event ledger before/after, process/file side-effect counter, recovered task state, reconciliation outcome. |
| **3. Provider continuity and routing honesty** | Two independently implemented provider families complete the same tool-calling fixture through the gateway. Ten tests covering explicit model change and eligible failover retain applied edits, tool outcomes, outstanding obligations, and approval state. Unsupported model capabilities surface before execution or as explicit errors; no silent dropping of required context or tools. | Canonical task state before/after, recorded route decisions, capability results, protocol fixtures, final diff/test equivalence. |
| **4. Review and budget integrity** | Every completed run exposes its diff identity, checks, failures/skips, and available usage. Editing a verified file makes the associated result stale. Ten budget-boundary fixtures launch no new billable request once committed spend plus reserved maximum request cost reaches the limit. Unknown pricing requires a token/request limit instead of a false monetary guarantee. Already-running work and unavoidable overshoot are displayed separately. | Evidence manifests tied to code revision/diff, stale-state assertions, admission ledger, pricing snapshot, reserved/actual/unknown usage reconciliation. |
| **5. Platform and gateway independence** | Fresh install/start, open repository, edit/test, stop/resume, and review smoke flows run on Windows, Linux, and macOS. The standalone gateway still passes its existing four-protocol, streaming, WebSocket, and configuration regression checks without installing the app. Label each platform separately as built, exercised, or unavailable. **macOS cannot pass the runtime gate until a Mac or macOS runner is actually available.** | Platform/architecture, package hash, installation log, runtime smoke results, gateway regression output. |

The deterministic recovery, routing, evidence, and budget tests should be stable release gates. Live-model task success is variable: report every attempt and failures, and repeat the task corpus before treating a single run as reliable performance evidence.

## When a competitive claim becomes justified

After Switchya passes its own milestone, run a larger predeclared corpus against pinned competitor releases. For harnesses that permit the same model, use the same model/provider configuration, starting revision, task prompt, budget, and tool/network access. For closed products where model parity is impossible, label the result a comparison of whole products rather than a harness-only comparison.

Measure accepted-task success, time to an independently passing change, human interventions, recovery success under the same interruptions, destructive or unintended actions, and cost per accepted result. Include failed runs in cost and time reporting. Repeat each task at least three times and disclose sample size and uncertainty; do not select only favorable examples. An illustrative claim such as “recovered 19/20 interruption cases in this published fixture” is defensible only after those tests exist and pass. “Best of the best” is not yet a supported claim.

Commercial validation is separate: repeated voluntary use and a reason users prefer this workflow to their current harness would support the product direction. Competitor pricing or adoption does not establish Switchya demand. This research did not test demand, perform a competitor hands-on benchmark, create accounts, spend money, or publish anything.
